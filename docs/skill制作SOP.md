# Skill 制作 SOP（覆盖多类型，skillforge 库通用）

这份文档规定在本库做新 skill 或改老 skill 的完整流程。所有类型的 skill 都走同一套主干，只在"怎么验证"和"配什么文件"上按类型分叉。

核心原则有两条。第一，skill 是给未来的 agent 看的可复用方法，不是记录你某次怎么解决问题的流水账。第二，没有先亲眼看到 agent 在没有这个 skill 时做错，就不知道这个 skill 该教什么，所以先写失败场景，再写 skill。

## 阶段 0：先判断要不要做成 skill

满足下面任一条才值得做：

- 这个方法不是一眼就能想到的，你自己也踩过坑。
- 以后别的项目还会用到，能跨项目复用。
- 其他人或其他 agent 也会遇到同类问题。

下面这些情况不要做成 skill：

- 一次性脚本、一次性任务，做完就扔的东西。
- 官方文档或现成 skill 已经讲清楚的标准做法，先查本地和开源有没有重复。
- 只对某个项目生效的约定，这类写进该项目的 AGENTS.md。
- 能用正则、类型检查、格式化工具自动卡住的机械规则，直接上自动化，别浪费文档去约束。判断类、取舍类的内容才值得写成 skill。

开工前先按全局规则查本地已装 skill 和 GitHub 开源项目，确认没有功能重叠的，再立项。

## 阶段 1：给 skill 定类型

类型决定后面用什么文件形态、怎么验证。真实 skill 常常是组合体，先定主类型，再补次要能力。

| 类型 | 解决什么问题 | 本地例子 | 主要文件 | 验证方式 |
| --- | --- | --- | --- | --- |
| 纪律约束型 | agent 明知规则却在压力下跳过 | tdd、verification-before-completion、santa-method | SKILL.md，必要时 references | 压力场景，看高压下是否仍守规则 |
| 技术方法型 | 一套可照做的操作步骤 | systematic-debugging、python-patterns、e2e-testing | SKILL.md，可带 scripts | 给新场景，看能否正确套用 |
| 思维模式型 | 一种看问题、做取舍的框架 | council、grilling、ponytail | 通常只有 SKILL.md | 识别场景加反例，看会不会乱用 |
| 参考文档型 | 按需检索的资料、API、语法 | obsidian-bases、context7、pdf | SKILL.md 加 references | 检索场景，看找得准、用得对 |
| 脚本执行型 | 确定性的重复操作或外部调用 | web-access、git-auto-sync、browser-use | SKILL.md 加 scripts 加 tests | 单元测试，先红后绿，真实跑通 |
| 素材模板型 | 生成产物要用的模板、样式、素材 | get-job、guizang-ppt、academic-cv-builder | SKILL.md 加 assets，可带 references | 对照产物验收清单逐项核对 |

一个 skill 可以同时占几类。比如 git-auto-sync 以脚本执行型为主，同时有纪律约束（禁止强推、预暂存检查）和参考文档（references/setup.md）。定类型时把主类型和附带能力都列出来。

## 阶段 2：RED，先写失败场景

这是 writing-skills 的铁律，新建和修改都适用。改老 skill 不先测，等于没测。

### 各类型怎么造失败场景

- 纪律约束型：设计压力场景，把时间紧、已经投入很多、人很疲惫、权威催进度这些压力组合起来。先不给 skill，让 agent 做一遍，逐字记下它用什么借口跳过规则。
- 技术方法型：给一个没见过的新场景，看 agent 不用这套方法时卡在哪、走错哪一步，记录具体缺口。
- 思维模式型：给该用和不该用的场景各几个，看 agent 能不能识别适用时机，重点记录乱用、误判的情况。
- 参考文档型：出检索题，看 agent 没有这份资料时找不到、找到后用错的地方，用来定资料的组织方式和关键词。
- 脚本执行型：直接先写测试，覆盖正常、边界、异常、故意捣乱的输入，先看它失败。测试放 skill 自己的 tests 目录。
- 素材模板型：先写产物验收清单，列出合格产物必须满足的点，再用没有模板的产物对照，看缺哪些。

### 没有子 agent 时的退化做法

不是每次都能开子 agent 跑压力测试，这时用三条替代：

1. 翻历史对话和踩坑日志里的真实失败记录，那些就是现成的基线。
2. 手动构造一个最小场景，自己按 agent 的思路走一遍，记录会在哪犹豫。
3. 对关键措辞做微测试，同一条指引换不同说法，每种至少重复 5 次，并且留一组不给任何指引的对照组。对照组都没出错，就说明这条指引没必要写，停手。单次样本会骗人，必须重复，命中结果要人工逐条看，不能只数数量。

## 阶段 3：命名和目录

### 命名硬规则

- 只用小写字母、数字、短横线，正则是 `^[a-z0-9-]+$`，不能用空格、下划线、中文、括号。
- 不能用短横线开头或结尾，不能有连续两个短横线。
- 不超过 64 字符，优先短的、动词开头的名字，比如 `creating-skills` 而不是 `skill-creation`，`root-cause-tracing` 而不是 `debug-helper`。
- skill 目录名和 frontmatter 里的 name 必须完全一致。

### 库内目录结构

每个 skill 自包含在 `skills/<skill名>/` 下：

```text
skills/<skill名>/
|-- SKILL.md      必需，技能说明
|-- agents/       可选，UI 元数据和调用策略
|-- scripts/      可选，可执行脚本
|-- references/   可选，按需加载的重资料
|-- assets/       可选，生成产物用的模板和素材
|-- tests/        可选，这个 skill 自己的测试
`-- docs/         可选，这个 skill 的 PRD、技术规格、复盘
```

没有实际用途的目录不要建，不放占位文件。库根的 `docs/` 放全库通用文档（比如本 SOP），skill 自己的开发文档放它内部的 `docs/`。

### 用脚手架初始化

skill-creator 自带初始化脚本，只申请真正需要的资源目录：

```powershell
$env:PYTHONUTF8='1'
D:\Anaconda\python.exe C:\Users\zyx\.codex\skills\.system\skill-creator\scripts\init_skill.py <skill名> --path skills --resources scripts,references
```

`--resources` 只列实际要用的，可选项是 scripts、references、assets。`--examples` 会生成示例文件，用完必须删掉，不能把示例当成品留下。已存在的 skill 不要重复初始化。

## 阶段 4：写 SKILL.md

### frontmatter 硬规则

校验器只允许这五个键：`name`、`description`、`license`、`allowed-tools`、`metadata`，写别的键直接判失败。

- name：按上面的命名规则。
- description：第三人称，只写"什么时候该用这个 skill"，不要总结它的流程。实测发现，description 里一旦写了流程摘要，agent 会照着摘要走，跳过正文。用"Use when..."或中文等价表述开头，写清触发条件、症状、场景，带上 agent 会搜的关键词，比如真实报错信息、工具名、文件名。
- description 不能出现尖括号，长度不超过 1024 字符，留 `[TODO:...]` 占位会被判失败。
- 整个 frontmatter 加起来控制在 1024 字符内。

### 正文怎么组织

常见结构，按实际需要取舍，不要硬凑：

1. 一两句概述，讲清核心原则。
2. 什么时候用，什么时候不要用，决策不明显时配一个小流程图。
3. 核心模式或方法，纪律型和方法型在这里给前后对比。
4. 快速参考，用表格或短列表方便扫读。
5. 实现方式，简单代码直接内联，重的逻辑链到脚本或 references。
6. 常见错误，写清会怎么错、怎么修。

### 形式要匹配失败类型

这是最容易写反的地方，按阶段 2 看到的基线失败选形式：

- agent 明知故犯、压力下跳规则：用明确的禁止项，加借口对照表和红旗自查清单。软话比如"建议""可以考虑"对这类失败没用。
- agent 做了但产物形状不对：给正面配方，直接规定成品长什么样、分几部分、什么顺序。只写"不要怎样"反而会诱发不想要的内容。
- agent 总漏掉某个要素：在它本来就要填的模板里留必填槽位，比在旁边写提醒管用。
- 行为要按条件变化：把规则挂在可观察的条件上，比如"如果 brief 文件存在就引用它"，不要写无条件规则再加一堆例外。

不要写模糊例外条款，比如"除非确实需要就可以不做"，这等于把谈判窗口重新打开。真有例外就单独写成一条条件规则。

### 渐进披露和篇幅

- SKILL.md 只放做决策需要的内容。配置步骤、排障手册、API 全表、长示例移到 references，在正文里给链接并写明什么情况下读它。
- 100 行以上的重资料、可复用脚本一律拆文件，不要全堆进 SKILL.md。
- 频繁加载的 skill 尽量压到 200 字以内，普通 skill 控制在 500 字上下，重的靠 references 分流。
- 引用别的 skill 只写名字并标明是不是必读，不要用 `@路径` 强加载，那会立刻把整个文件灌进上下文。

### 明确不要写的东西

- 不写"某次会话里我们发现"这种叙事故事，要的是可复用规律。
- 同一段示例不用多种语言各写一遍，一个能跑的好例子胜过五个半成品。
- 流程图节点里不写代码，代码放代码块。
- 不用 step1、helper2 这类没语义的标签。
- 不复制 AGENTS.md 已经强制的全局规则，也不重复别的 skill 讲过的内容。

## 阶段 5：配套文件怎么配

### scripts

只有同一套逻辑会被反复重写、或者需要确定性执行时才写脚本。外部调用、网络、数据库、文件读写必须有错误处理，这不是过度设计：

- 所有外部调用设超时，默认 30 秒，不许无限等。
- 失败最多重试 3 次，间隔按 1 秒、2 秒、4 秒递增，还失败就明确报错并给替代方案。
- 禁止空 try except 吞异常，至少要记日志。
- 密钥、Token 只走环境变量或 .env，代码里绝不硬编码，.env 必须在 .gitignore 里。
- 脚本必须有测试，关键停止条件和状态码要能被测试覆盖，参考 git-auto-sync 的 sync.py 和它的测试。

### references

放只在特定场景才需要读的资料，比如配置手册、API 文档、分模式指南。每个 references 文件都要在 SKILL.md 里有入口，写清什么时候读它，避免 agent 要么全读、要么找不到。同一条信息只在一个地方维护，不要正文和 references 各写一份。

### assets

放的是生成产物时要用的东西，比如模板、字体、图片、PPT 骨架、示例工程。assets 是被加工的原料，不是给 agent 的指令，不要把操作说明写进 assets。

### agents/openai.yaml

这是给软件界面和调度器读的配置，不是给 agent 读的。字符串值加引号，键不加引号。常用字段：

- interface 下的 display_name、short_description、icon_small、icon_large、brand_color、default_prompt，default_prompt 要显式带上 `$skill名`。
- dependencies.tools 声明依赖的 MCP 等外部工具。
- policy.allow_implicit_invocation 默认是 true，保持自动发现。只有用户明确要求"只能手动调用"时才设成 false，设了之后仍可用 `$skill名` 显式触发。不要因为操作敏感就默认关掉隐式触发，敏感动作靠执行前要授权来管。

改这个文件优先就地改字段，不要整文件重新生成，避免覆盖已有的 policy 和 dependencies。完整字段说明看 `C:\Users\zyx\.codex\skills\.system\skill-creator\references\openai_yaml.md`。

## 阶段 6：GREEN，分类型验证

### 所有 skill 必过的格式门禁

```powershell
$env:PYTHONUTF8='1'
D:\Anaconda\python.exe C:\Users\zyx\.codex\skills\.system\skill-creator\scripts\quick_validate.py skills/<skill名>
```

Windows 必须带 PYTHONUTF8，否则中文按 GBK 解码会报错。看到 `Skill is valid!` 才算过。校验器只查 frontmatter、命名和未完成占位，不代表这个 skill 的决策质量没问题。

### 分类型验证重点

| 类型 | 必须验证什么 |
| --- | --- |
| 纪律约束型 | 阶段 2 的压力场景带 skill 重跑，看高压下是否守规则；记录新借口，补进对照表，反复到稳定 |
| 技术方法型 | 给训练时没见过的新场景，看能否独立套用；再给缺信息的场景，看指引有没有漏洞 |
| 思维模式型 | 正例、反例都测，确认该用时识别得出，不该用时不硬套 |
| 参考文档型 | 出检索题，确认能定位到正确条目并正确使用，常见任务都能覆盖 |
| 脚本执行型 | 单元测试覆盖正常、边界、异常、恶意输入，先红后绿；脚本在真实环境跑通一次 |
| 素材模板型 | 用模板生成真实产物，对照验收清单逐项核对，再查格式、截断、乱码 |

### 收尾验证

- 措辞类改动用微测试收口，5 次以上重复，带无引导对照组，人工看每一条结果。
- 装到 `C:\Users\zyx\.codex\skills\` 后重启 Codex，跑一次最小真实调用，确认能被发现、能正常触发。
- 有外部依赖的（Python 包、CLI、MCP server）逐项确认已安装、版本对得上。
- 完成前遵守 verification-before-completion：测试和校验要在当前这轮真跑过、看到通过输出，才能声称完成，不能靠"应该没问题"。

## 阶段 7：开源发布门禁（本库全程公开，硬规则）

本库远程公开，每次提交前都要过这道门：

1. 全仓扫描凭据，确认没有 .env、密钥、Token、私钥、个人敏感信息。命中就停下来交用户判断，不提交。
2. .env 在 .gitignore 里；需要给配置模板时用 .env.example，只写变量名不写真值。
3. 文档和示例里不出现真实密码、Token、内部地址，一律用占位符。
4. 许可证用库根的 MIT，skill 子目录不单独放 LICENSE，除非这个 skill 用了不同许可证。
5. 新建 GitHub 仓库前，分别向用户确认仓库名和公开或私有，两项都明确才动手，不默认公开，不凭本地目录名替用户决定。已有仓库不自动改名、不改可见性。
6. 在库根 README 的 skill 索引表加一行，写清名字、作用、目录链接。
7. 禁止强推，不自动 merge 或 rebase，远程分叉时保留本地提交并报错。
8. 提交说明用简体中文，写清改了什么、为什么，不用 update、auto commit 这类没有信息量的模板。
9. 推送走当前可用代理。本机代理端口变动过，先确认端口在监听；需要临时指定时用 `git -c http.proxy=http://127.0.0.1:<端口> -c https.proxy=... push`，不擅自改全局代理配置。

## 阶段 8：部署和迭代

- 个人使用：把整个 skill 目录复制到 `C:\Users\zyx\.codex\skills\`，重启 Codex。
- 判断装全局还是项目级：别的项目还会用到就装全局，只服务某个项目的专属 skill 放该项目的 `.codex/skills/`。
- 修改现有 skill 同样走 RED 到 GREEN，先复现没有这条规则时的问题，再改，再验证，不允许"只加一小节就不测"。
- 一次只做一个 skill，做完验证、部署、确认可用，再开下一个，不批量生产未测的 skill。
- 用户的纠正和踩坑按四要素记进 skill 自己的 docs 或库根 MEMORY.md，可复用的规则沉淀回 SKILL.md，密钥只记录存放位置，不记录值。

## 一页清单（每个 skill 逐项勾选）

立项：

- [ ] 确认不是一次性任务，能跨项目复用，本地和开源没有重复。
- [ ] 定了主类型和附带能力，对照六类表选好文件形态和验证方式。

RED：

- [ ] 写了失败场景，记录了 agent 没 skill 时的真实错误或借口。
- [ ] 脚本型先写测试并看到失败；纪律型有压力场景；其他类型有对应基线。

结构：

- [ ] 名字符合 `^[a-z0-9-]+$`，不超 64 字符，目录名和 frontmatter 一致。
- [ ] 只建了实际需要的目录，没有占位和残留示例。
- [ ] frontmatter 只用五个允许键，description 只讲触发条件、无尖括号、不超 1024 字符。
- [ ] 指引形式匹配失败类型，没有模糊例外条款。

GREEN：

- [ ] quick_validate 输出 Skill is valid。
- [ ] 按类型完成对应验证，脚本型测试覆盖正常、边界、异常、恶意输入。
- [ ] 装到本机后重启，最小真实调用能触发。

发布：

- [ ] 凭据扫描零命中，.env 已忽略，文档只用占位符。
- [ ] README 索引表已更新，许可证用库根 MIT。
- [ ] 中文提交说明，本地与远程核对一致，没有强推。
